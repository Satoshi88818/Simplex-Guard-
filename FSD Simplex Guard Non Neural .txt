Simplex Guard — Non-Neural Runtime Safety Monitor

A from-scratch, independently testable implementation of the "Simplex Guard" component described in the FSD v12 design document (Improvement #5). This is not a neural network — it is a small set of closed-form physics checks (time-to-collision, stopping distance, lateral-acceleration limits) that can override the AI planner's output with a provably conservative fallback trajectory.

Everything below was actually written, executed, and debugged in a sandbox — including two real bugs the test suite caught (details in the "Bugs found during testing" section). This is not a hypothetical description of code; it's the real code and the real pytest run.

1. Why this component, and what it does

The rest of the FSD v12 stack (MapFormer, the flow-matching planner, the GNN social layer, the NCBF safety filter) is neural and therefore fundamentally hard to formally verify. The Simplex architecture pattern addresses this by putting a small, deterministic, analytically provable supervisor after the neural stack, with the authority to throw away the neural output entirely and substitute a safe fallback.

This guard checks, at every planning cycle:

CheckWhat it catchesTime-to-collision (TTC)An imminent collision with something ahead, using a hard threshold (1.5 s) and an earlier soft threshold (3.0 s)Required stopping distanceWhether the vehicle can physically stop in time given its speed, reaction/actuation latency, and available friction-limited decelerationLateral acceleration feasibilityWhether the planner's commanded speed on a given curvature would exceed the tire-friction budget (skid risk)Sensor sanity (NaN/Inf)Corrupted upstream sensor/planner data — fails safe instead of computing garbage physics 

When a check fails, the guard doesn't just flag it — it generates a replacement trajectory analytically:

Frontal danger → constant-deceleration straight-line stop (comfort or emergency profile depending on severity)

Cornering-speed danger → same path, speed clipped to the safe cornering limit for the current curvature and estimated road friction

2. Design principles

Every decision is a closed-form function of physical quantities. No learned components, no floating hyperparameters that aren't physically motivated (each threshold in the config is documented with its reasoning).

Deterministic. Same inputs → same outputs, always. This is a prerequisite for the kind of testing a real ASIL-D argument needs.

Conservative by construction. When uncertain, the guard is allowed to be wrong toward caution (intervene) but never toward danger (fail to intervene) for the checks it claims to cover.

Fail-safe on bad input. NaN/Inf sensor data triggers an automatic emergency-stop fallback rather than propagating garbage through the physics or crashing.

No pure ML framework dependency. Deliberately implemented in plain Python + NumPy (no PyTorch) so the core logic stays small enough to audit line-by-line, and could realistically be ported to a restricted-subset language (e.g. MISRA C) for a real certification effort without dragging a deep learning framework along with it.

3. Bugs found during testing (real, not illustrative)

Writing adversarial tests against the first draft immediately surfaced two genuine safety-relevant bugs, which is exactly the point of building the test suite this way rather than only testing the happy path:

Bug 1 — fabricated clearance from the scan boundary. The obstacle-scanning function originally returned max_range_m when no obstacle was found within the sensor's range. A caller would then compute TTC = max_range_m / speed, producing a specific, confident- looking number for a region of road that was never actually observed to be clear — it was just the edge of where the sensor stopped looking. At high speed with a short scan range this produced a plausible-looking-but-fabricated TTC. Fixed by having the scan return None on "nothing found," and the guard treats None as "no data," not "confirmed clear."

Bug 2 — NaN sensor input crashed instead of failing safe. Passing a NaN speed (a realistic sensor-glitch scenario) caused an unhandled ValueError deep inside the range-scan arithmetic (int(nan) is invalid). A safety monitor that crashes on bad input is worse than one that's merely wrong — a crash means no supervision at all. Fixed by adding an explicit sensor-sanity check at the top of check_and_override: any non-finite value in the ego state or candidate trajectory now immediately routes to the emergency-stop fallback instead of reaching the physics code at all.

Both are now locked in as regression tests (test_scan_boundary_is_not_mistaken_for_observed_clearance, test_nan_speed_in_ego_state_forces_safe_fallback, and two related NaN/Inf cases) so they can't silently reappear.

""" simplex_guard.py ----------------- A non-neural, analytically-verifiable runtime safety monitor ("Simplex architecture" pattern: a high-performance, unverified controller supervised by a simple, provably-safe fallback controller that can override it). Design goals (in priority order): 1. Every decision is a closed-form function of physical quantities (speed, distance, friction, curvature). No learned components, no floating hyperparameters that aren't physically motivated. 2. Deterministic and side-effect free: same inputs -> same outputs, always. Required for certification-style testing (ASIL-D style argument depends on this). 3. Conservative by construction: when uncertain, it is allowed to be wrong in the direction of caution (intervene) but never wrong in the direction of danger (fail to intervene) for the checks it claims to cover. 4. Fast: O(B * T) with small constants, safe to run at high rate on a CPU thread with a hard real-time budget. This module intentionally does NOT depend on torch/numpy-heavy ML infrastructure so it can be audited, unit tested, and (in a real certification effort) ported to a restricted-subset language (e.g. MISRA C) without dragging along a deep learning framework. Coordinate conventions ----------------------- - Ego-centric frame at the *current* planning instant: x = forward (m), y = left (m), heading = 0 rad along +x. - Trajectory state per timestep: (x, y, heading, speed, curvature) x, y : position (m), ego frame at planning time heading : heading angle (rad), 0 = straight ahead speed : longitudinal speed (m/s), signed (>=0 expected) curvature : path curvature (1/m), signed (+ = turning left) - Occupancy grid: 2D boolean/float array, shape (H, W), ego-centric, with the ego position at (origin_row, origin_col) and cell (i, j) covering the physical point: x = (j - origin_col) * resolution y = (origin_row - i) * resolution i.e. row index decreases as x increases is NOT assumed; we index by explicit origin + resolution so the convention is unambiguous and tested (see tests for exact mapping). """ from __future__ import annotations import math from dataclasses import dataclass, field from enum import Enum from typing import List, NamedTuple, Optional, Sequence, Tuple import numpy as np # -------------------------------------------------------------------------- # Configuration # -------------------------------------------------------------------------- @dataclass(frozen=True) class SimplexGuardConfig: """All thresholds are physically motivated and documented with the reasoning behind the chosen value. In a real program these would be set (and re-verified) by a formal hazard analysis / FMEA, not picked by an engineer's judgement call — the values here are reasonable defaults for a passenger vehicle, clearly labelled as such, and every one is overridable. """ # --- Time-to-collision (TTC) --- # NHTSA / SAE literature commonly treats TTC < 1.5s as an imminent # crash regime for forward collision warning systems; we use 1.5s # as the hard trigger and 3.0s as an early/soft trigger band. ttc_hard_threshold_s: float = 1.5 ttc_soft_threshold_s: float = 3.0 # --- Driver/system reaction + actuation latency budget --- # Time between "guard decides to intervene" and "commanded # deceleration is actually being produced by the vehicle" # (brake actuator lag, communication latency, etc). actuation_latency_s: float = 0.15 # --- Braking physics --- # Max achievable deceleration is mu * g, derated by a safety # margin because mu estimates are noisy and we don't want to plan # trajectories that assume the theoretical limit. gravity_mps2: float = 9.81 friction_default: float = 0.7 # dry asphalt, conservative default friction_derate: float = 0.85 # use 85% of mu*g as "available" decel min_clearance_m: float = 2.0 # minimum standoff distance, stopped # --- Lateral / cornering --- # Fraction of friction budget allowed to be spent on lateral accel # before the guard considers the corner unsafe at the commanded # speed. Kept flat and simple so it is trivial to log, serialize, and unit test.""" overridden: bool violations: Tuple[ViolationType, ...] fallback_mode: FallbackMode ttc_s: Optional[float] required_stopping_distance_m: Optional[float] available_clearance_m: Optional[float] max_lateral_accel_mps2: Optional[float] commanded_lateral_accel_mps2: Optional[float] # -------------------------------------------------------------------------- # Core physics helpers (pure functions — the auditable core) # -------------------------------------------------------------------------- def time_to_collision(distance_m: float, closing_speed_mps: float) -> Optional[float]: """TTC = distance / closing_speed. Returns None (i.e. "no TTC concern") if the gap is not closing (closing_speed <= 0) or if already at/behind the obstacle in a degenerate way handled by the caller. Never divides by zero. """ if closing_speed_mps <= 1e-6: return None if distance_m <= 0.0: return 0.0 return distance_m / closing_speed_mps def required_stopping_distance( speed_mps: float, decel_mps2: float, reaction_time_s: float, ) -> float: """Distance needed to come to a full stop from `speed_mps`, given a reaction/latency window during which speed is assumed constant (worst case: no deceleration yet applied), followed by constant deceleration `decel_mps2`. d = v * t_reaction + v^2 / (2 * decel) """ if decel_mps2 <= 0: raise ValueError("decel_mps2 must be > 0") speed_mps = max(speed_mps, 0.0) reaction_distance = speed_mps * reaction_time_s braking_distance = (speed_mps ** 2) / (2.0 * decel_mps2) return reaction_distance + braking_distance def lateral_acceleration(speed_mps: float, curvature_per_m: float) -> float: """a_lat = v^2 * kappa. Sign follows curvature sign.""" return (speed_mps ** 2) * curvature_per_m def max_safe_cornering_speed( curvature_per_m: float, max_lateral_accel_mps2: float ) -> float: """Max speed such that |v^2 * kappa| <= max_lateral_accel. Returns +inf for (near-)straight paths. Returns the distance (m) to the first occupied cell, or `None` if nothing is found within `max_range_m`. Returning `None` (rather than `max_range_m`) on a miss is a deliberate safety choice: silently substituting the scan boundary for "clear" would let a caller compute a spurious, falsely reassuring TTC/clearance number from a distance that was never actually observed to be clear. Callers must treat `None` as "no obstacle detected within sensing range" and must not manufacture a TTC from it. This is intentionally a simple, easily-reasoned-about sweep (not a learned occupancy-to-distance regressor) so its correctness can be argued directly from the grid semantics. Heading and curvature are held at their current values (straight-line braking is the safest default fallback: it does not introduce a new lateral-accel risk). Returns array of shape (horizon_steps, 5). """ traj = np.zeros((horizon_steps, 5), dtype=np.float64) v = max(ego_speed_mps, 0.0) x = 0.0 for t in range(horizon_steps): traj[t, 0] = x traj[t, 1] = 0.0 traj[t, 2] = heading_rad traj[t, 3] = v traj[t, 4] = 0.0 # zero curvature: hold lane, no new turn risk # advance x += v * dt_s - 0.5 * decel_mps2 * dt_s ** 2 v = max(v - decel_mps2 * dt_s, 0.0) return traj def generate_speed_limited_trajectory( base_trajectory: np.ndarray, max_speed_mps: float ) -> np.ndarray: """Clip a candidate trajectory's speed profile to a safe cornering speed, leaving position/heading/curvature untouched. """ out = base_trajectory.copy() out[:, 3] = np.minimum(out[:, 3], max_speed_mps) return out # -------------------------------------------------------------------------- # The guard itself # -------------------------------------------------------------------------- class SimplexGuard: """Stateless (per-call) analytical safety supervisor. Clearance / TTC / stopping-distance check --------- ttc = None req_stop_dist = None avail_clearance = None if occupancy is not None: h, w = occupancy.shape origin_row, origin_col = occupancy_origin or (h // 2, w // 2) max_range = required_stopping_distance( speed_mps=max(ego_speed, 1.0), decel_mps2=cfg.fallback_comfort_decel_mps2, reaction_time_s=cfg.actuation_latency_s, ) + 20.0 # generous scan range beyond worst-case stop raw_clearance = nearest_obstacle_distance_ahead( occupancy=occupancy, origin_row=origin_row, origin_col=origin_col, resolution_m=resolution_m, heading_rad=ego_heading, half_width_m=cfg.ego_half_width_m, max_range_m=max_range, ) if raw_clearance is None: # Nothing detected within sensing range: genuinely no # TTC/stopping-distance concern. Lateral acceleration feasibility over the horizon -- speeds = candidate_traj[:, 3] curvatures = candidate_traj[:, 4] lat_accels = speeds ** 2 * curvatures worst_idx = int(np.argmax(np.abs(lat_accels))) worst_lat_accel = float(lat_accels[worst_idx]) if abs(worst_lat_accel) > max_lat_accel: violations.append(ViolationType.LATERAL_ACCEL) # --- 3. Decide fallback ------------------------------------- fallback_mode = FallbackMode.NONE safe_traj = candidate_traj overridden = False has_ttc_hard = ViolationType.TTC_HARD in violations has_stop_dist = ViolationType.STOPPING_DISTANCE in violations has_lat = ViolationType.LATERAL_ACCEL in violations has_ttc_soft = ViolationType.TTC_SOFT in violations if has_ttc_hard or has_stop_dist: fallback_mode = FallbackMode.EMERGENCY_STOP safe_traj = generate_stop_trajectory( ego_speed_mps=ego_speed, decel_mps2=cfg.fallback_emergency_decel_mps2, horizon_steps=T, dt_s=dt_s, heading_rad=ego_heading, ) overridden = True elif has_lat: safe_speed = max_safe_cornering_speed( curvature_per_m=curvatures[worst_idx], max_lateral_accel_mps2=max_lat_accel, ) fallback_mode = FallbackMode.SPEED_LIMIT_CORNER safe_traj = generate_speed_limited_trajectory(candidate_traj, safe_speed) overridden = True elif has_ttc_soft: fallback_mode = FallbackMode.COMFORT_STOP safe_traj = generate_stop_trajectory( ego_speed_mps=ego_speed, decel_mps2=cfg.fallback_comfort_decel_mps2, horizon_steps=T, dt_s=dt_s, heading_rad=ego_heading, ) overridden = True if not violations: violations = [ViolationType.NONE] decision = GuardDecision( overridden=overridden, violations=tuple(violations), fallback_mode=fallback_mode, ttc_s=ttc, required_stopping_distance_m=req_stop_dist, available_clearance_m=avail_clearance, max_lateral_accel_mps2=max_lat_accel, commanded_lateral_accel_mps2=worst_lat_accel, ) return decision, safe_traj, overridden # """ B = candidate_traj_batch.shape[0] decisions: List[GuardDecision] = [] out_traj = np.zeros_like(candidate_traj_batch, dtype=np.float64) overridden_flags = np.zeros(B, dtype=bool) for b in range(B): occ_b = occupancy_batch[b] if occupancy_batch is not None else None mu_b = mu[b] if mu is not None else None decision, safe_traj, overridden = self.check_and_override( candidate_traj_batch[b], ego_state_batch[b], occ_b, dt_s, resolution_m, mu_b, ) decisions.append(decision) out_traj[b] = safe_traj overridden_flags[b] = overridden return decisions, out_traj, overridden_flags

8. What this is not, and what real deployment would still need

This is a solid, honestly-tested reference implementation of the logic of a Simplex-style guard — it is not a certified safety system. Turning it into one would additionally require:

A formal hazard analysis (FMEA / STPA) to justify every threshold in SimplexGuardConfig, rather than the reasonable-but-asserted defaults documented here.

Execution on independent, certified hardware separate from the AI compute path (the whole point of Simplex is diverse redundancy).

Porting to a language/runtime with a qualified toolchain (MISRA-C or similar) if targeting automotive ASIL-D, since Python/NumPy has no such certification story.

Integration testing against the real occupancy grid, perception uncertainty, and ego-state estimation pipelines — this implementation uses a clean, well-documented sensor interface, but a real system's actual sensor noise characteristics need to be tested against, not assumed.

Independent third-party audit — a safety monitor cannot self-certify.
